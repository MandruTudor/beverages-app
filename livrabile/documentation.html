Abstract

Beverages App este o aplicație web pentru catalogarea și gestionarea băuturilor, construită pe o arhitectură PHP pură fără framework, cu bază de date SQLite. Sistemul implementează autentificare cu JWT și sesiuni PHP, control al accesului pe două roluri (user / admin), operații CRUD complete pentru băuturi și categorii, upload de imagini, import CSV și JSON, liste de cumpărături personale și de grup, preferințe cu rating, statistici și integrare cu API-ul Open Food Facts. Interfața frontend este construită în PHP și JavaScript vanilla, fără niciun framework JS.

1. Introducere

Aplicația a fost concepută ca un catalog interactiv de băuturi (ceaiuri, sucuri, smoothie-uri, infuzii etc.) cu posibilitatea de a gestiona categorii, ingrediente, alergeni, regimuri alimentare, locații de vânzare, preferințe personale și de grup, și liste de cumpărături. Platforma este destinată atât utilizatorilor obișnuiți (care pot naviga, evalua și salva băuturi), cât și administratorilor (care pot adăuga, edita, șterge băuturi și gestiona utilizatorii).

Din punct de vedere tehnic, proiectul demonstrează utilizarea PHP fără framework (arhitectură proprie în 4 straturi), gestionarea unei baze de date SQLite cu relații many-to-many, securitate prin JWT, hashing BCrypt, protecție XSS și injecție SQL, precum și interactivitate frontend prin JavaScript asincron (Fetch API, Promise.all, debounce, paginare client-side).

2. Arhitectura aplicației

Aplicația adoptă o arhitectură stratificată în 4 niveluri: Controller → Service → Repository → DTO, inspirată din principiile MVC și DDD, dar implementată manual în PHP pur, fără niciun framework.

2.1 Structura directoarelor

Separarea în straturi are rolul de a izola responsabilitățile: controllerul nu cunoaște SQL-ul, repository-ul nu cunoaște regulile de business, iar service-ul nu cunoaște HTTP-ul. Aceasta permite testarea și modificarea fiecărui strat independent.

2.2 Fluxul unei cereri HTTP

Un exemplu complet pentru POST /api/beverages.php (adăugare băutură):

  1. api/beverages.php — instanțiază dependențele și apelează controllerul: 
    $ctrl = new BeverageController(
    new BeverageService(
        new BeverageRepository(get_db())
    )
);
$ctrl->handle(get_param('action') ?? '');
  2. BeverageController::handle() — folosește match(true) pentru rutare bazată pe metodă HTTP + prezența parametrului id: 
    match(true) {
    $isGet  && !$id => $this->list(),
    $isGet  &&  $id => $this->get($id),
    $isPost             => $this->create(),
    $isPatch &&  $id => $this->update($id),
    $isDel   &&  $id => $this->delete($id),
};
  3. BeverageController::create() — parsează corpul JSON cu json_body(), construiește un BeverageCreateDto, apelează BeverageService::create().
  4. BeverageService::create() — apelează require_admin() (returnează 403 dacă utilizatorul nu este admin), validează câmpurile, apelează BeverageRepository::create() urmat de 4 apeluri sync*() pentru relațiile many-to-many.
  5. BeverageRepository::create() — execută un INSERT cu statement pregătit PDO, returnează ID-ul noii înregistrări.
  6. json_response() — serializează răspunsul ca JSON cu codul HTTP corespunzător și exit.

Autoloading-ul claselor este asigurat de includes/autoload.php, care înregistrează un callback cu spl_autoload_register() ce caută fișierul clasei în directoarele controllers/, services/, repositories/ și dto/.

2.3 Stratul includes

includes/db.php — Singleton PDO

Funcția get_db() implementează pattern-ul Singleton cu o variabilă statică $pdo. La prima apelare creează conexiunea SQLite, aplică trei PRAGMA în ordinea obligatorie: busy_timeout = 10000 (înainte de WAL pentru a evita race condition), journal_mode = WAL (scrieri concurente), foreign_keys = ON. Dacă fișierul bazei de date nu există, execută init.sql pentru a crea schema și a insera datele seed. Migrațiile lazy sunt aplicate atomic în BEGIN/COMMIT.

includes/helpers.php — Utilitare HTTP

Exportă: json_response($data, $status=200) și json_error($msg, $status=400) (ambele setează header-ul Content-Type: application/json și apelează exit); json_body() (decodifică JSON din php://input); missing_field($fields, $data) (returnează primul câmp lipsă); get_param($key) (citire din $_GET); sanitize($str) (trim + strip_tags).

includes/auth.php — Sesiuni și garduri de acces

session_init() pornește sesiunea PHP cu cookie HttpOnly; SameSite=Strict. login_user($user) scrie datele utilizatorului în $_SESSION și apelează session_regenerate_id(true) pentru a preveni session fixation. require_auth() verifică mai întâi un token Bearer JWT în header-ul Authorization (pentru cererile API din JS) și apoi sesiunea PHP (pentru paginile PHP). require_admin() apelează require_auth() și verifică rolul.

includes/jwt.php — Token-uri JWT

Implementare manuală HS256 (HMAC-SHA256). jwt_generate($payload) construiește header-ul și payload-ul ca JSON, le codifică în Base64URL, calculează semnătura cu hash_hmac('sha256', …, JWT_SECRET, true) și concatenează cele trei părți separate de puncte. jwt_validate($token) recalculează semnătura și o compară cu hash_equals() (protecție timing attack), verifică câmpul exp. jwt_from_request() extrage token-ul din header-ul HTTP și apelează jwt_validate().

Important: JWT nu criptează datele, ci le semnează. Payload-ul este vizibil în clar (Base64URL decodabil), dar nu poate fi falsificat fără cheia secretă.

3.2 Constrângeri și integritate referențială

SQLite nu activează cheile externe implicit. Fiecare conexiune PDO execută PRAGMA foreign_keys = ON. Comportamentul la ștergere este diferit în funcție de contextul semantic:

  • ON DELETE CASCADE — pentru tabelele de legătură (ex.: beverage_ingredients): ștergerea unei băuturi șterge automat toate legăturile ei.
  • ON DELETE SET NULL — pentru beverages.category_id: ștergerea unei categorii nu șterge băuturile, doar le dezasociază.

Constrângeri suplimentare notabile: CHECK(rating BETWEEN 1 AND 5) pe user_preferences.rating și group_preferences.rating; UNIQUE(user_id, beverage_id) pe user_preferences (un utilizator are o singură preferință per băutură).

Pattern-ul sync pentru relații N:M

La crearea sau actualizarea unei băuturi, relațiile many-to-many sunt sincronizate prin metode de tip syncIngredients(), syncAllergens(), syncVenues(), syncDietaryRegimes() din repository. Fiecare metodă execută un DELETE urmat de INSERT OR IGNORE cu subquery: 

DELETE FROM beverage_allergens WHERE beverage_id = ?;
INSERT OR IGNORE INTO beverage_allergens (beverage_id, allergen_id)
    SELECT ?, id FROM allergens WHERE id = ?;

Subquery-ul previne inserarea ID-urilor invalide (dacă clientul trimite un ID inexistent, SELECT nu returnează niciun rând și INSERT nu se execută).

3.3 Date seed

Fișierul init.sql este învelit într-o tranzacție BEGIN / COMMIT pentru atomicitate. Toate inserările folosesc INSERT OR IGNORE — dacă datele există deja, comanda nu eșuează și nu creează duplicate. Datele seed includ: 6 utilizatori (toți cu parola password, hash BCrypt), 8 categorii, 8 regimuri alimentare, 7 alergeni, 20 ingrediente și băuturi de exemplu.

4. Backend — implementare

4.1 Autentificare și autorizare

Fluxul de înregistrare

  1. JS trimite POST /api/auth.php?action=register cu JSON {username, email, password}.
  2. AuthController::register() apelează missing_field() și delegă la AuthService::register().
  3. Service-ul validează: format email cu filter_var(), lungime minimă parolă ≥ 8 caractere, unicitate username/email în baza de date.
  4. Parola este hashată cu password_hash($password, PASSWORD_BCRYPT) — BCrypt generează automat un salt random și produce un hash de 60 caractere.
  5. Utilizatorul este creat cu rolul implicit user.

Fluxul de autentificare

  1. JS trimite POST /api/auth.php?action=login cu {email, password}.
  2. AuthService::login() caută utilizatorul după email cu findByEmail().
  3. Verifică parola cu password_verify($password, $user['password_hash']) — BCrypt recalculează hash-ul cu saltul stocat și compară. Dacă email-ul sau parola sunt greșite, răspunsul este identic (nu se dezvăluie care dintre ele).
  4. Apelează login_user($user): scrie datele în $_SESSION și regenerează ID-ul sesiunii (session_regenerate_id(true)) pentru a preveni session fixation.
  5. Generează un token JWT cu payload {user_id, username, email, role, iat, exp} și îl returnează clientului. JS îl stochează în localStorage sub cheia jwt_token.

Verificarea autentificării la fiecare cerere API

require_auth() din includes/auth.php verifică mai întâi header-ul Authorization: Bearer <token> (folosit de JS prin Fetch API). Dacă token-ul este valid și neexpirat, utilizatorul este autentificat. Dacă nu există token Bearer, verifică $_SESSION['user_id'] (folosit de paginile PHP renderizate server-side). Dacă niciuna nu este prezentă, returnează HTTP 401. require_admin() apelează require_auth() și verifică suplimentar că role === 'admin', altfel returnează HTTP 403.

4.2 Modulul Beverages

Listare cu filtre dinamice (BeverageRepository::findAll)

Interogarea SQL este construită dinamic prin acumularea condițiilor în array-ul $where[] și a parametrilor în $params[], în funcție de filtrele trimise (categorie, alergeni, regimuri, sezon, regiune, preț minim/maxim). Câmpurile allergen_count și regime_count sunt calculate cu subqueries SQL pentru a permite filtrarea combinată: 

SELECT b.*,
  (SELECT COUNT(*) FROM beverage_allergens
   WHERE beverage_id = b.id AND allergen_id IN (…)) AS allergen_count
FROM beverages b
WHERE allergen_count = 0   -- exclude băuturile cu alergeni selectați
AND …

PATCH cu semantică parțială (BeverageCreateDto)

DTO-ul folosește metoda has($field) pentru a distinge între un câmp lipsă (clientul nu vrea să îl modifice) și un câmp cu valoare null (clientul vrea să îl șteargă). Aceasta permite cereri PATCH care actualizează doar câmpurile trimise, fără a le reseta pe celelalte.

Integrare Open Food Facts

La crearea unei băuturi, dacă este furnizat un cod de bare, service-ul interogează API-ul public Open Food Facts pentru a prelua automat informații despre produs (ingrediente, alergeni, imagine). Rezultatele sunt fuzionate cu datele din formular.

4.3 Alte module API

4.4 Upload imagini

Endpoint-ul api/upload.php acceptă fișiere prin multipart/form-data. Validarea tipului MIME nu se bazează pe extensia fișierului (falsificabilă), ci folosește extensia PHP finfo cu constanta FILEINFO_MIME_TYPE pentru a detecta tipul real din conținutul binar al fișierului. Tipurile acceptate: image/jpeg, image/png, image/webp, image/gif. Limita de dimensiune este 2 MB. Numele fișierului salvat este generat cu uniqid('bev_', true) pentru a evita coliziunile și pentru a preveni traversarea directoarelor.

4.5 Export și RSS

api/export.php permite descărcarea întregului catalog ca fișier CSV sau JSON. api/rss.php generează un feed RSS 2.0 valid cu cele mai recente băuturi adăugate, permițând abonarea la actualizări din orice client RSS.

5. Frontend — implementare

5.1 Pagini PHP

Toate paginile vizibile utilizatorului se află în directorul pages/. Fiecare pagină PHP aplică garda de autentificare server-side (prin require_auth() sau require_admin()) înainte de orice output HTML. index.php din rădăcina proiectului redirecționează automat spre pages/dashboard.php sau pages/login.php în funcție de starea sesiunii.

Paginile care afișează conținut dinamic în funcție de rol transmit informația spre JavaScript prin atributul data-role pe elementul <body>: 

<body data-role="<?= htmlspecialchars($user['role']) ?>">

JS citește document.body.dataset.role și afișează sau ascunde butoanele de administrare corespunzătoare. Aceasta este protecție vizuală; protecția reală este aplicată server-side prin require_admin() în fiecare endpoint API.

5.2 auth.js

Gestionează autentificarea și înregistrarea în browser. Principalele componente:

  • apiFetch(url, body) — wrapper peste Fetch API pentru cereri POST JSON; returnează {ok, status, data}.
  • initPasswordStrength() — evaluează parola cu 5 criterii (lungime ≥ 8, lungime ≥ 12, majuscule, cifre, caractere speciale); actualizează vizual un indicator de tip bară colorată (Prea slabă → Excelentă).
  • initLoginPage() — previne submisia nativă cu e.preventDefault(), validează câmpurile local, apelează apiFetch(), stochează token-ul JWT în localStorage.setItem('jwt_token', data.token) și redirecționează spre dashboard.
  • initRegisterPage() — validare live a confirmării parolei, plus aceleași etape ca login.
  • DOMContentLoaded — apelează ambele funcții init*(); fiecare verifică dacă formularul său există pe pagină și iese imediat dacă nu.

5.3 beverages.js

Cel mai complex fișier JS al proiectului, gestionează pagina de catalog. Stare globală: allBeverages, categories, dietaryRegimes, userLists, myPreferences (dicționar {beverage_id: pref}), currentPage, ITEMS_PER_PAGE = 9.

  • Inițializare paralelă — Promise.all([…6 apeluri API…]) la DOMContentLoaded pentru a reduce timpul de așteptare: categorii, alergeni, regimuri, locații, liste cumpărături și preferințele proprii se încarcă simultan.
  • Strategia de filtrare hibridă — filtrele de categorie, alergeni, regim, sezon, regiune și preț sunt trimise ca parametri server-side (reduc volumul de date din rețea). Căutarea text liberă se aplică client-side pe allBeverages deja încărcat, cu debounce de 300 ms pentru a evita cereri excesive.
  • Paginare client-side — renderPagination() calculează paginile vizibile cu un algoritm cu elipsă, afișând întotdeauna prima și ultima pagină plus contextul paginii curente.
  • Modal detalii — openDetail(id) face Promise.all([getBeverage, getLists]) și randează HTML-ul complet în modal, inclusiv stele interactive pentru rating (initDetailStarPicker()) cu handlere mouseenter/mouseleave/click.
  • openForm vs initFormSubmit — separate intenționat: openForm(id) deschide modalul și îl populează (poate fi apelat de mai multe ori), iar initFormSubmit() adaugă listener-ul de submit o singură dată la inițializare. Dacă ar fi în aceeași funcție, fiecare deschidere a modalului ar adăuga un nou listener, ducând la trimiteri multiple ale formularului.
  • Upload imagine — folosește fetch() direct (nu funcția api()) cu FormData pentru multipart/form-data; token-ul JWT este atașat manual în header-ul Authorization.
  • escHtml() — înlocuiește &, <, >, ", ' cu entitățile HTML corespunzătoare, prevenind XSS la inserarea datelor din API în DOM.

5.4 admin.js

Gestionează panoul de administrare (utilizatori, import CSV, import JSON).

  • api(method, url, body) — diferit de beverages.js: aruncă Error la răspuns non-OK, în loc să returneze {ok, data}. Atașează automat token-ul JWT.
  • loadUsers() — randează tabelul de utilizatori cu innerHTML, apoi apelează attachUserListeners(). Ordinea este importantă: listener-ii trebuie adăugați după ce DOM-ul tabelului există.
  • Import CSV — parseCSV() este un parser complet care tratează câmpuri cu ghilimele, ghilimele duble escapate și BOM UTF-8. Previzualizarea arată primele 5 rânduri; importul trimite fiecare rând ca cerere POST individuală la api/beverages.php.
  • Import JSON — acceptă array direct sau obiect {beverages: […]}; validează prezența câmpului name înainte de import.

6. Securitate

Prevenire injecție SQL

Toate interogările SQL folosesc prepared statements PDO cu parametri legați (? sau :name). PDO separă codul SQL de date, eliminând posibilitatea ca datele utilizatorului să fie interpretate ca instrucțiuni SQL. Nu există nicio concatenare de string-uri în interogările SQL.

Prevenire XSS (Cross-Site Scripting)

Orice dată provenită din surse externe (API, baza de date) care este inserată în HTML trece prin escHtml() în JavaScript sau htmlspecialchars() în PHP. Aceasta transformă caracterele speciale HTML în entități, astfel încât un script malițios (<script>…</script>) ajunge în DOM ca text vizibil, nu ca cod executabil.

Hashing parole (BCrypt)

password_hash($password, PASSWORD_BCRYPT) generează un salt aleatoriu de 22 caractere și aplică algoritmul BCrypt (cost factor implicit: 10). Hash-ul final de 60 caractere include saltul și cost factor-ul. La autentificare, password_verify() extrage saltul din hash stocat, recalculează și compară. Stocarea parolelor în clar este imposibilă — hash-ul este ireversibil.

JWT — autentificare fără stat (stateless)

Token-ul JWT permite cererilor API din JavaScript să se autentifice fără a depinde de cookie-uri sau sesiuni PHP. Token-ul este semnat cu HMAC-SHA256 folosind o cheie secretă stocare server-side; orice modificare a payload-ului invalidează semnătura. Compararea semnăturilor se face cu hash_equals() pentru a preveni atacurile de tip timing attack. Token-urile au câmp exp (expirare), verificat la fiecare cerere.

Session Fixation

session_regenerate_id(true) este apelat la autentificare, generând un nou ID de sesiune și invalidând cel vechi. Aceasta previne atacul în care un atacator forțează un utilizator să folosească un ID de sesiune cunoscut.

Validare MIME tip imagini

Extensia fișierului nu este un indicator de securitate (poate fi falsificată). finfo_open(FILEINFO_MIME_TYPE) analizează primii bytes ai fișierului (magic bytes) pentru a determina tipul real, indiferent de extensia declarată.

Autorizare dublă

Butoanele de administrare sunt ascunse în UI pe baza rolului (data-role), dar fiecare endpoint API sensibil apelează independent require_admin() server-side. Un utilizator malițios care ar bypassa UI-ul și ar trimite cereri direct la API ar primi HTTP 403.

7. Funcționalități avansate

Statistici

Pagina pages/stats.php afișează grafice generate cu biblioteca Chart.js: distribuția băuturilor pe categorii, distribuția pe regiuni, prețul mediu per categorie și distribuția alergenilor. Datele sunt furnizate de api/stats.php cu interogări SQL agregate.

Liste de cumpărături

Listele pot fi personale (group_id = NULL) sau aparținând unui grup. Articolele dintr-o listă pot fi bifate (checked = 1), permițând urmărirea progresului de cumpărare. Autocomplete-ul din câmpul de căutare a articolelor folosește debounce pentru a limita cererile API.

Grupuri de utilizatori

Utilizatorii pot crea grupuri, invita alți utilizatori și gestiona preferințe și liste de cumpărături comune. Apartenența la grup este gestionată prin tabela de legătură group_members.

Import în masă

Administratorii pot importa băuturi din fișiere CSV sau JSON prin drag-and-drop sau selecție clasică. Previzualizarea arată primele 5 rânduri înainte de import. Importul se face rând cu rând, cu raportarea succeselor și erorilor.

Feed RSS

api/rss.php generează un feed RSS 2.0 valid cu cele mai recente 10 băuturi adăugate, permițând urmărirea actualizărilor din orice client RSS.

Integrare Open Food Facts

Prin furnizarea unui cod de bare la adăugarea unei băuturi, aplicația interogează automat API-ul public Open Food Facts și preia date despre produs (ingrediente, alergeni, imagine), reducând efortul de completare manuală.

8. Concluzie

Beverages App demonstrează că o arhitectură web robustă poate fi construită în PHP pur, fără dependențe externe, respectând principii fundamentale de inginerie software: separarea responsabilităților, securitate în profunzime, și o interfață utilizator interactivă construită cu JavaScript vanilla. Proiectul acoperă un spectru larg de concepte web moderne: autentificare stateless cu JWT, hashing criptografic, relații de baze de date complexe, programare asincronă în browser și integrare cu API-uri externe.
